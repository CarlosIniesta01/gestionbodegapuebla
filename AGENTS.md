
- Operations catalog: global families/operations live in familias_operativas/operaciones_catalogo (bodega_id NULL = global, set = centre-owned); per-centre enablement in centro_operaciones where a missing row means enabled. Why: one master catalogue, independent centre config, no duplicates.
- Catalogue capability flags (requiere_*/admite_*) are descriptive only; tipo_formulario decides which existing form opens (carga/descarga always reuse OrdenLogisticaDialog). Why: Bloque A must not touch stock, consumos or movimientos.

- Global catalogue rows (bodega_id NULL) are created/edited/toggled only with permission operaciones.catalogo.global (admin/enólogo), enforced in RLS, server functions and UI; centre roles only toggle centro_operaciones. Why: a centre must never alter the master catalogue for other centres.
- Every trabajo launched from a catalogue operation (including embotellado's own dialog) stores operacion_catalogo_id. Why: uniform classification across families.
- New-work centre is chosen in SelectorOperacionDialog and passed as bodegaId to every form (independent of the global active centre); createTrabajo/embotellado validate access, operation enabled and deposits of that centre server-side. Why: send work orders to any centre without switching context.
- Quick-access work buttons open SelectorOperacionDialog filtered by tipo_formulario; global views (isGlobal) list trabajos from every authorised centre and cards/details use the trabajo's own bodega_id. Why: one multicentre path, never the session centre.
- tipo_formulario 'traslado_intercentros' (F06-08) has no form yet: selector disables it and validarOperacionCentro rejects it server-side. Why: an intercentre transfer must never be saved as an ordinary trasiego.
- Assignments live only in trabajo_trabajadores (one trabajo, many rows); never delete rows: retiring sets activa=false/estado 'retirado'. Rules (centre membership, gestor via has_permission 'tareas.asignar', operator may only accept/reject own with motivo, one active row per operario, one active responsable) are enforced by trigger tt_guard + partial unique indexes. Why: single assignment system with full history.
- Per-user internal notices go to public.notificaciones, written only by SECURITY DEFINER triggers with a unique dedupe_key; schedule/instruction edits go through RPC actualizar_programacion_trabajo (audited). Why: no duplicate notices, no client-side writes.
- B2 reusable work templates keep versioned technical forecasts in trabajos.datos.planificacion; the shared server helper validates centre-scoped references and recalculates doses before creation, while specialised logistics/bottling forms remain unchanged. Why: reuse the existing order and assignment model without physical execution or parallel stock logic.
- B2 multi-operation orders store versioned operation forecasts and one product-line list in trabajos.datos.multioperacion; compatibility follows supported template topology and each operation is centre-validated. Why: one existing work ID and B1 assignment system, without replacing specialised forms.
- B2 preliminary actuals are append-only trabajo_eventos of type b2_uso_preliminar; database triggers enforce own active assignment, centre, lot, expiry, cumulative availability, duplicate protection and audit. Why: preserve forecasts and worker identity without creating consumption or stock writes before B3/C.
- Worker invitations use centre-scoped invitation rows and existing Auth accounts; a self-authenticated RPC activates memberships only after email verification and sign-in, without overwriting existing access. Why: invitations must never grant unauthenticated access or duplicate accounts.
- Load privileged Auth clients inside server handlers after centre-admin validation; send invitation links to the public activation page on the published origin. Why: admin credentials must stay server-only and email activation must not depend on the editor session.
